# 独立求解器计算架构审查：2026-11-08

最新同场 20 对 20 测量中，**自研与 HRC 达到 CI10 的时间基本相同，自研每百万样本的进程 CPU 成本约低 10.3%**。首次达标分别为 285.727 秒和 286.604 秒，亚秒差异不足以宣称显著超越，且双方计时边界存在差别。完整复核见第 10 节。当前更值得推进共享策略读取、写同步和桶映射的隔离实验；已完成的调度计量与 ETW 不支持优先重写抢块机制。

现有结果已排除“这棵三人树主要慢在保存”这一解释；它们还不能证明新的主要瓶颈恰好是某一条除法、递归栈或锁。按原版写法逐条移植也不等于最快：原子读、串行写、独立缓存的混合架构已有实测收益，而全 CAS 更新、缩小 choose 临界区等候选没有获得同样收益。

本报告只读生产代码与既有日志。另按主代理授权构建了隔离调度计量版本并做短正确性验证；没有修改生产、重跑 CI10、改变优先级或 CPU 亲和性、安装 profiler、操作用户应用。计量版吞吐和扰动由主代理统一测量；收到结果后的独立解释见第 8 节。

## 3. 代码中的剩余结构与优先级

### P0：建立当前版本的调度与 CPU 工作量证据

`native/hrc_parallel.hpp:30–43` 已让 worker 自主抢 250 样本块；`:139–155` 仍在每个控制片段等待全部 worker。主循环 `native/hrc_research_solver.cpp:770` 给片段 50ms 截止，之后检查取消、CI、输出、保存。它已消除了每批 250/worker 的固定汇合，不能再用旧架构批评当前实现。

两次正式运行的 `elapsed - rounds*50ms` 分别约 21.24 秒、9.36 秒，均约 3.1%。这只是额外墙钟的粗分解，包含最后一个片段、尾部、控制工作、CI、输出和保存。**不是**每个 worker 的真实等待占比，也不是整个调度优化的严格收益上限；CPU 工作与空闲还可能重叠。它足以说明不能仅凭 50ms 字样承诺大倍数加速。

已准备第 6 节隔离计量：分别测启动延迟、worker 最早/最晚结束跨度、每个 worker 结束到控制线程确认全员结束的等待、controller collect 与片段间控制时间。下一步根据结果决定是否延长 worker 连续驻留到下个 CI/保存/取消边界，或者维持 50ms 但减少启动/退出调度成本。

### P0：构建身份必须能区分编译器和参数

**事实：** `preflop_lab/hrc_native.py:43–64` 的缓存身份只哈希 CPP/headers；`:50` 命中已有 EXE 即返回。编译器版本、`-O3`、目标 CPU、PGO 数据和编译参数并没有进入该身份。若只改 flags 而不改 native 源文件，可能拿旧 EXE 当新候选测速。

这目前是**实验可信度与可复现性问题**，不是已经测到的运行时间瓶颈。尝试 PGO 或 CPU target 前，先将完整命令、compiler fingerprint、目标架构、profile digest 和源码纳入独立构建身份，保留 EXE SHA。不要通过覆盖正在使用的 EXE 解决。

### P1：把运行时共享数据布局与持久化格式分开

**事实：** Node 已 `alignas(64)`，写端更新计数在独立 cache line (`native/hrc_research_solver.cpp:76–108`)；默认 23/25 无锁定/频率约束走原子读取 (`:111–176`)，更新仍由 NodeMutex 串行化 (`:436–438`)。这一混合路径避免 CAS 写竞争，也保留单写者普通平均策略/访问计数写入。

**剩余候选：** 默认 23 的一个 bucket 仍按 `[R(k),D,A(k)]` 相邻放在 canonical raw 数组，23/25 的总 counter 与首部/首行也接近。即使 Node 元数据已经分线，读 regret 的核与写平均/denominator 的核仍可能共享 raw cache line；不同行也可能落在同一条 64B line。默认 25 本身平均是 shared header，不应错误描述为逐 bucket A；它的布局改动要单独评估。

可尝试单独的 runtime regret arena、counter 行和 writer-only average/denominator/visits 区域，保存时映射回原 canonical 格式。保持串行 writer 和原数值顺序；不重试已表现一般的“全 CAS”或“桶锁”方案。不是建议把每个 bucket 都填充到 64B：那可能扩大工作集、增加 TLB/cache 压力。先测当前 read/update 成本及不同布局的缓存流量替代指标，再比较紧凑 SoA 或小块布局。

**风险/验收：** counter 的偶发刷新时序、负/NaN/zero normalizer、格式 27/31/63、锁定、reset/discount、CI flush、hrcz float32 导入、续跑和预算均要保持。普通 23/25 可先走候选，其他配置使用旧格式路径；单线程完整 checkpoint/RNG 必须逐字节一致，并行比较质量不能要求历史 interleaving 相同。尚无本轮 PMU cache-miss/coherence 证据，因此不能写成“已证实主要热点”。

### P1：有依据地压缩执行路径与代码布局

`scalar/vector` (`native/hrc_research_solver.cpp:545–565`) 每次递归仍经过 Node 获取、终局/常量判断、hand、choose、模型/锁定路径，再更新。当前每副牌约 63 次 scalar+vector 调用。它们频繁是事实；每种检查/内存访问的 CPU 比例尚未测量。

可以考虑在一次训练配置固定后，构造不可变的紧凑运行视图，预先决定普通 23/25、模型、静态桶/动态桶、约束等路径，以减少训练内重复条件。它与已经测过但未证明收益的“仅把 MAXA=16 换成 k2/k3 模板”不同：目标是减少每节点跨结构读取和配置分支，而不是只缩栈帧。若增加函数指针、模板代码体积或更多缓存元数据，也可能更慢；应先用当前版本的低扰动阶段采样筛选。

编译器已有 `-O3 -std=c++17 -ffp-contract=off` (`hrc_native.py:57`)；没有显式 PGO/LTO/CPU target 参数。不能仅凭命令就假定 Zig 默认没有启用某条硬件指令。单个巨大 translation unit 已包含多数 header，单开 LTO 未必获得很大额外空间。更可检验的候选是代表性 early+mature profile 驱动的函数/基本块布局、冷热代码分离或目标架构编译。必须保持 `ffp-contract=off`、禁止 fast-math，并先修构建身份。PGO 训练与评价不能只用同一短轨迹。

### P2：调度持久驻留，仅在测得等待后推进

若新计量显示大量 tail/launch 等待，可把 worker 持续运行至明确事件，而非无条件每 50ms 全员停止。控制线程通过独立 stop generation/pause token 请求 quiescence；每 250 样本边界响应，CI/save/reset 只在全员结束后执行。保持精确 completed samples、每 worker RNG、异常后全部停止和 checkpoint rollback。

不能直接把 250 改大再称“去掉 barrier”；大块会放大快慢核尾部差和取消延迟。也不能只盯尾部最慢 worker，忽略有些 worker 启动晚、抢不到块或 OS 抢占。若计量证明这部分很小，应让位给共享存储和 CPU 工作量优化。

### P3：突破兼容架构的批量/设备路线

真正大幅超过现有 CPU 求解器可以研究 frontier/wavefront 批量遍历、SIMD 同构节点或 GPU 样本批次，但这会触及在线 regret 更新的可见性和顺序，不再是低风险等价替换。当前小树、稀疏深度分支、共享策略持续更新不保证适合 GPU；必须先建立算术量/内存流量/分支与数据搬运成本模型。若做，应作为独立算法实验，报告策略质量/样本效率和吞吐，而非把顺序变化掩饰成“完全相同”。本轮不优先投入。

## 4. 不再重复的候选与易误用证据

- 狭窄 choose 临界区、通用 reciprocal 余数、常数 bound 分支没有稳定净收益；不因表达式看起来贵而再宣称除法瓶颈。
- 全 CAS 写、细粒度桶锁没有在已有统一测试中胜过当前 reader-atomic/writer-serial 选择；没有新的争用证据不重开。
- k2/k3 递归模板、固定 update 展开、简单 hoist、sentinel eager 替代都已做过筛选，收益弱或反向。Node 独立写 cache line、静态映射、短表读取、terminal pointer cache 已被接纳，不能当作下一步尚未做的工作。
- `reports/hrc-throughput-round3-phase-profile-20261108.json` 是**旧整 choose 锁版本**。计量本身令训练从 3.9385 秒变为 4.3232 秒，约 +9.77%。它的 197m choose/55m update 调用数解释了为什么优先查读取，但估算阶段时间是含抢占的 worker 墙钟；不能把该份阶段比例直接称为当前 accepted20 的 CPU 火焰图。
- 该旧 profiler 的很多短事件接近时钟粒度，扣空时钟开销也不能自动得到无偏 CPU 时间。新调度计量故意测较粗的 block/slice，不逐递归计时。

## 5. 独立列出的 CI 计时边界问题

`Engine::poll_ci` (`native/hrc_research_solver.cpp:578`) 先计 `ci_snapshots()` 的耗时，再调用 `Tracker::update`，所以传给 Tracker 的 duration **不包含 update 本身**。`native/hrc_ci.hpp:46` 用该 duration 设置 `interval=max(15000,duration*50)` 和 `last_time=now+duration`。已审原版完整 measurement 包含更多工作。

这不是本轮对公式做过的新修改，也不能把差异全部归因于速度。建议单独修复/验证计时责任：记录完整 snapshot+drift computation，然后在保持历史公式的前提下更新 measurement end/next interval；避免用测量结束后才知道的 duration 反过来改变本次用于 drift 的起始 timestamp。补合成时钟边界测试：不足间隔不更新、精确阈值、历史保留、超过 300ms 时自适应间隔、重启等。三人当前 interval=15s，尚未证明此差异会改变实际触发间隔；超大树可能更重要。不要把这个修法混入一次纯吞吐候选，免得 CI 停止边界一起变化。

## 6. 已交付的隔离调度计量版本

目录 `.research-cache/architecture-review-20261108/scheduler-profile/`，生成器 `../make_scheduler_candidate.py`，验证器 `../validate_scheduler_candidate.py`。生产文件保持不变。

- EXE `solver.exe` SHA256 `80b439bcee5f085c687e1f9e895c7aa40e541263e8c4bb862b2623fd280dfde6`。
- 参数 `argv22=0` 为关闭，`1` 为开启；省略也关闭。同一个 EXE 比较 on/off，再以冻结生产 EXE 作 shadow，分开看计量扰动和编译代码布局变化。
- off 在 `work()` 入口分派，原 `adaptive_work()` 循环保留，不在 off 每个 block 内增加统计分支。
- on 每个 worker 一个 `alignas(64)` 私有记录；每个 slice 两次 worker 时钟，controller 发布/全员结束/collect 边界时钟。每 64 个块按 worker 索引错开相位抽取一次 claim/work 时钟；不消耗 solver RNG。不存逐 deal 日志。
- 全部 worker 本地记录块数、已领取样本、完成样本、CAS 重试；完成数取该 worker Engine 的实际 samples 差值。Controller 仅在 quiescent 后合并读取。异常仍在所有 worker 停止后传播。
- 最终 stdout 多一行 `kind=scheduler_profile`；原 finished 行保留。全部统计不进入 checkpoint，也不改变策略语义。并发交错仍会受观察影响，不承诺多线程 checkpoint 逐位相同。

字段意义：

| 字段 | 含义与限制 |
|---|---|
| `launch_delay` | controller 发布起点到 worker 开始 work；含 OS 调度/锁唤醒，不等于 CPU 指令时间 |
| `work_wall` | worker 进入至退出的墙钟；包括节点锁等待和抢占 |
| `worker_exit_spread` | 同一 slice 最早与最晚 worker 结束之差 |
| `retired_wait` | 某 worker 退出到 controller 确认全部退出的时间；包括 controller 被延迟唤醒，并非纯 barrier 忙等 |
| `controller_collect` | 全员确认后至 collect 完成；包含 ticket 计数等少量控制记账 |
| `controller_gap` | 上次 collect 完成至下一次发布；包含文件检查、CI、日志、保存及 OS 抢占 |
| `deadline_tail` | deadline 后到 controller 确认全员结束的正部分；最后样本预算耗尽可能为 0 |
| `sampled_block_claim/work` | 每 64 块确定性相位抽样的墙钟；不是 IID，不外推为全进程 CPU 占比 |

直方图实际桶上界随 JSON 输出：第 0 桶 `{0}`，后续正桶 `(previous_upper, upper]`，上界 1ns、2ns、4ns…，末桶 overflow 上界 null。正有限桶分位只能定位到该区间，除首桶外上下界约相差 2 倍；它不提供精确 p99。各 metric 同时保存 count/sum/max，可以精确算均值但仍是墙钟。

19 项短验证通过：2/8 线程精确预算、正常 deadline、外部 pause、保存/续跑、两条调度路径异常后全员停止、终局计数；三个实际 3p 单线程 1000 样本运行（production、candidate off、candidate on）的完整 checkpoint 一致。串行运行没有 ParallelTrainer，所以这一项验证候选主程序没有引入其他语义变化；它不单独证明计量的并发顺序不变。并发 on 路径由预算、状态、异常和 histogram 断言覆盖。证据 `scheduler-profile/validation.json` 与各 case 的 `validation/*/result.json`。

本候选额外诊断内存没有合并到产品的树预算，是明确标记的隔离 observer overhead；它只为这次充足预算的测试使用，不应直接移植到产品。未尝试 MSVC 编译，现有 Zig/Clang 编译 flags 与生产一致。

## 7. 下一轮可操作验收顺序

1. 主代理顺序运行 mature 同 checkpoint、同 20 线程、同预算，production shadow/off/on 各三次，交错次序；不与 HRC 或另一训练并行。保留完整 stdout、进程 CPU/RSS、实际 EXE hashes、起始 checkpoint hash，求 on/off 扰动区间。计量开关显著改变速度时先降低抽样频率，不能直接相信被扰动的分布。
2. 先读每 worker completed deals、工作墙钟、launch/retired wait、claim retries。计算控制时间和尾部的可恢复范围，不把总 worker wall 相加后当进程 wall。混合 P/E 核的工作量不均要与 OS 调度区分；若需要补当前处理器抽样，先另申请 CPU 窗口，不改亲和性。
3. 若控制/尾部小，优先做默认 raw 分区和代表性 PGO 的两个独立候选；若尾部大，先事件驱动驻留。每次只有一个架构变量，early/mature 都测，串行完整状态/原版数值探针先过。
4. 吞吐筛选通过后才跑同场 20 线程完整 CI10。比较真实达到目标时间、CPU 工作量、样本数、CI 轨迹，并继续原版/自研按手牌的策略与 EV 代价验证。CI 通过不能替代准确性比较，也不能把更少采样简单解释为质量更高。

没有硬件计数器或当前细粒度 CPU/调度 profile 之前，本报告不承诺下一项能提高多少。现有数字已经能支持优先级，尚不能支持“所有时间都耗在某个模块”这样的结论。

### 8.4 这次证据改变了什么

**降低“先重做抢块/去掉 50ms 全员控制”的优先级。** 已观测启动+退场约占 worker 可用墙钟 3.44%，collect 极小，领取争用也低。它们有优化空间，但没有支持将它们当成当前大幅差距主因。

**下一次测量应看 work 内部的 on/off-CPU 及热点。** 96.56% worker 墙钟在 work 内部，而进程平均约 9.5 个逻辑 CPU，这两种口径不能直接相减成某个模块的时间。缓存 miss 的 CPU stall 一般仍计入该线程 CPU 时间，不能拿较低平均 CPU 占用直接证明内存瓶颈。若主代理使用隔离 ETW，应同时观察 Thread/Ready/CSwitch 与 CPU stack，区分线程尚未运行、内部 yield/同步、后台抢占和实际计算；只采 CPU 栈会漏掉 off-CPU 时间。

因此保留共享存储布局、节点写同步及编译布局为候选，但在获得新的当前版本证据前，不把其中任何一个写成已量化主因，也不据本次快照解释此前所有波动。

## 9. 当前版本 ETW 证据：读取与写同步成为优先项

同线程从 out 到 next-in 的 off 区间，按 next-in 恢复栈关联到 `Engine::update` 3.62248 worker 秒、condvar 2.12948 worker 秒。Microsoft 的 [CPU Analysis](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/cpu-analysis)支持将 incoming NewThreadStack 与该线程先前间隔联合分析；它不是同时被切出的另一个线程的栈。报告保留“恢复调用链关联，而非直接因果”标签是正确的。WrYieldExecution 且 Ready 的区间共 3.55609 worker 秒，约占共同 worker 墙钟 6.624%；这提供写同步/让步路径值得调查的依据，未证明一个锁持有者或可消除的加速量。

该窗口 on-CPU 47.30136 秒、off-CPU 6.38430 秒，内窗平均 17.62 个逻辑 CPU，进程全窗平均约 15.33。此前调度计量约 9.5 的平均 CPU 并未被这次快照“解释掉”；两次负载/时段不同，不能跨运行凑成一个成本分解。

下一轮优化应保持生产冻结的基线，按共享 raw 运行时布局/读取路径、写同步等待策略、桶映射分别做隔离候选；先通过数值/完整状态回归，再同场测 early+mature 的 CPU 秒/样本和 wall 吞吐，最后进行匹配线程数的完整 CI10 与策略质量比较。不要因为已查到热点就绕过测量，也不要重新大范围试过所有被淘汰候选。

### 10.3 下一步架构优先级

1. **共享策略读取/运行时存储布局。** 当前 ETW 的 `strategy_atomic` exclusive 样本约 24.68%，优先审查真实热点机器指令，再单独试验 R 与 A/D 的运行时隔离或读取路径。没有 PMU 数据，不能先认定缓存失效占了该百分比。候选必须保留规范序列化、预算、约束/格式回退及串行数值语义。
2. **写同步与让步策略。** 当前 ETW 同时发现 `Engine::update` 热点及 WrYieldExecution ready 区间；下一实验应联合 on/off-CPU 和更新调用链。14.71% exclusive 不是纯锁成本，恢复栈关联也不是等待原因的唯一证明。不重复将全 CAS、曾失败的缩小 choose 临界区等旧候选直接当成改善方案。
3. **桶映射和编译布局。** `bucket_from_row` 约 8.39%、`prepare_bucket_row` 约 4.75%，可以独立考察读取与映射开销；代表性 PGO/LTO 属待测候选，先把编译器、flags 与 profile 身份纳入构建键。不能根据函数名称推断整数除法就是瓶颈。
4. **调度和控制继续保留为次级候选。** 既有 60m 调度计量的 claim CAS 重试仅 0.0279%，启动+退场约占 worker 墙钟 3.44%，collector 成本很小。没有新证据前，不优先重写自主领块；这些墙钟比例也不是可直接兑换的 CPU 或加速比例。

可执行验收仍是每次一个架构变量，先数值/完整状态与并发边界回归，再相同自有 checkpoint 的 early/mature 交错重复短测，记录 CPU 秒/样本与墙钟，最后做独立初始化的完整 CI10 与策略质量比较。新版本若改变异步读写顺序，串行逐位通过不能被外推为并行策略质量等价。此次结果已经缩小速度差距；要宣称稳定超过原版，还需要重复同场证据和质量评估，而不是把亚秒优势或较低 CPU 用量直接当成最终结论。
