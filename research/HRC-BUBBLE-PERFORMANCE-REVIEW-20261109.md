# EP bubble 子树：代码复核与原版 HRC 20 线程计时

复核结论：针对这手牌的默认 MTT ICM、20 线程 EP 子树，目前没有找到已证实能轻易再带来 2 倍收益的问题。这个结论不代表 2 倍提升不可能，也不代表已经达到 CPU、缓存或内存带宽上限。更换并行写入架构、减少达到同等质量所需的采样量，仍有研究空间，但尚无本负载上的实测收益。

## 原版 HRC 已实际运行至 CI＜10

2026-11-09，原版 HRC 重新通过 Start Hand from Save File 建立计算，完成自身的自动 1,000 万次全树初始化后，选择 UTG 弃牌后的 EP 决策，运行 HRC 4.0 (Default)、Selected Subtree、Until CI value is reached、CI Target 10.0。Reset Regret 和 Reset Strategies 均未勾选。明确设置 20 线程并重启生效，启动前界面和运行时设置均验证为 20。

这次没有直接续跑用户已收敛的存档。与我们的流程一样，正式计时不包含先前的初始化。两边独立初始化，因此冻结的 UTG 策略和随机轨迹不同。

原版从点击 OK 前计时，到首个 CI＜10 记录为 1,014.972 秒；首个已空闲界面观察为 1,016.179 秒；观察器经过第二次空闲确认后结束于 1,017.182 秒。最后一次活动观察到首次空闲观察相隔约 3.065 秒。这些是外部墙钟边界，不冒充原版内部训练计时。

本次正式开始时间为 2026-11-09 11:24:04 北京时间。HRC 全程平均使用约 18.41 个逻辑 CPU，观察到的最大工作集约 5.95 GiB。我们的上述正式运行原生训练时间合计 1,193.875 秒，应用墙钟包含两次加载、建表和保存，共 1,259.74 秒。

按这些记录，我们的正式应用耗时约为 HRC 的 1.240 倍，即多用约 24% 时间；正式采样量多约 3.43%。这只是本次运行的比较，不能视为消除了初始化、CI 历史、随机轨迹和机器状态影响后的纯内核速度比。

我们的被比较版本为 `033dc7741886ae9e70743c99ae3b17d9666db17410f98e3da00c6f04c4b40808`，已经包含共享货币终局表。最近接受的发牌缓冲复用和组合查表优化，另有固定工作量约 3.7% 的训练提速证据，但尚未重新完整跑到 CI10，所以这里没有把预测值列为实测值。

## 确认树、配置与子树边界一致

用户原存档、新建后的初始化存档、本次最终存档的 `settings.json` 字节完全一致。124,659 个节点解析后，ID、父节点、孩子次序、动作、玩家、街道及终局类型逐项全部一致；共 58,192 个决策节点。原存档与重建存档的物理序列化次序不同，因此不能只比较 `gametree.dat` 原始 SHA256 来判断树是否相同。

所选 EP 决策为原生节点 1，路径 `[0]`，包含 82,610 个节点，其中翻前决策 2,278 个。HRC 的界面说明与实现均表明，Selected Subtree 从所选动作**之前**的决策开始：选择 EP raise 2bb 行，包含 EP 弃牌、加注、全下的所有后续分支。它不是仅求 EP 已经加注后的延续。

最终保存后再做纯字节比较：EP 子树外的 42,049 个节点记录全部保持不变，子树内 37,009 个节点记录改变。这直接支持此次原版确实只更新了所选 EP 子树。原存档的完整 SHA256 也保持不变。

## 已复核的明显开销

| 项目 | 源码和测量证据 | 本次判断 |
|---|---|---|
| 训练在 Python 中运行 | 训练、遍历、策略更新在原生 C++ 中；Python 管理任务 | 没有这一层明显瓶颈 |
| 每个线程复制整棵树 | `ParallelTrainer` 共享节点、只读拓扑及表；随机数和工作缓存独立 | 没有整树复制问题 |
| 策略读取都争抢互斥锁 | 默认无锁定条件的策略使用 relaxed 原子读取；写入仍按节点同步 | 读取路径已有优化；写竞争仍待测量 |
| 每个终局反复进行完整 ICM 结算 | 这手牌启用 34,224,104 字节共享终局表；正式运行 `terminal_settlements=0` | 先前最大的重复工作已移出训练热路径 |
| 发牌临时分配及逆向组合计算 | 最近已接受缓冲复用和组合查表；完整单线程检查点逐字节相同，96 项相关测试通过 | 已有小幅收益，未发现倍数收益 |
| 检查点保存过于频繁 | 两段正式训练保存共 44.540 秒，占原生训练 3.73% | 即使保存零成本，训练上限约 1.039 倍 |
| 每次启动重新建表 | 两段建表共 45.868 秒 | 可优化续跑体验，但不足以翻倍 |
| 线程数不合适或训练主要串行 | 探索性线程扫描中 20 线程最快；实际原生并行训练存在 | 不能据此宣布并行效率已最优，也未找到靠减少线程翻倍的证据 |
| 手牌评估、终局去重、直接终局边 | 已做候选与顺序对照；没有稳定的显著训练收益 | 未启用失败候选，不能把理论减少的行数当成速度收益 |

以完整正式运行的原生训练计时，减去保存后为 1,149.335 秒。相对于 1,259.74 秒应用墙钟，假设两次启动、准备和训练保存的所有已计量开销都归零，也只相当于约 **1.096 倍**。这不是整体优化潜力上限，而是这组外围开销的上限；继续寻找 2 倍收益需要减少剩余的训练工作或单位工作成本。

## 尚未解决的研究问题与适用范围

1. 整节点写锁是否对不同手牌桶产生了不必要的等待，需要针对这手牌测量竞争时间与缓存行传递。更细的锁、私有增量合并或批量更新不能仅凭 CPU 占用率决定；它们可能改变异步训练轨迹和收敛速度。
2. 当前没有本负载的内存带宽、末级缓存未命中、停顿周期等硬件计数器证据。高 CPU 利用率和较高内存占用不能证明硬件上限。
3. 要评估采样或更新算法的大提升，应比较同等质量所需的总时间；固定次数吞吐与时间到 CI 必须分开。CI 是策略变化诊断，不是可利用度证书，同一个 CI 门槛也不证明两个结果具有完全相同的策略误差。
4. 此结论限于当前默认 MTT ICM EP 负载。原生终局表目前有 64 MiB 上限，若另一棵树放不下完整表，可能回落到慢路径；这手牌的表约 32.6 MiB，未触发此问题。FGS、抽水等其他模型的优化覆盖也不同，不能据此宣布所有模式都没有明显问题。
5. 之前三人桌的调度或 ETW 热点比例不是这手牌的独占时间分解；带计时器的阶段剖析也不能把嵌套时间相加，当成硬件瓶颈证据。
